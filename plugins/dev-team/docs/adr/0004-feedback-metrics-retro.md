# 0004: フィードバックは提案型、計測は GitHub 正・スクリプト集計、振り返りはオンデマンド

- ステータス: accepted（2026-08-15）

## 背景
レビュー指摘を開発時の観点に反映するフィードバックループ、開発効率の計測、ループを俯瞰したスキル改善の提案が要件にある。誤った学習の蓄積や、読まれない長い報告は避けたい。

## 決定
- フィードバックは提案型。dev-loop は指摘を review-log に記録するだけ。dev-retro が繰り返し出た指摘（同 category が閾値以上、または人の指摘）を根拠付きでルール文案にし、プロダクトの開発ルール文書への PR を出す。教訓ファイルへの自動追記はしない
- 計測は GitHub を正とし、集計は `scripts/metrics.mjs` が行う。LLM に集計させない。サブエージェントの往復など GitHub に痕跡が無いものは events.jsonl / review-log から補完し、欠けていれば「不明」と表示する
- 振り返りは `/dev-team:dev-retro` でオンデマンド実行。dev-loop の終了報告には振り返り推奨シグナルだけ添える

## 検討した選択肢
- 教訓ファイルへの自動追記: 誤った教訓が人の目に触れず蓄積し、実装がおかしくなるリスク
- events.jsonl を計測の正にする: 端末ローカルで、セッションや端末をまたぐと欠ける
- 毎ループ終了時にフル振り返り: コストが高く、報告が長くなって読まれなくなる

## 影響
- 開発ルール文書が「dev-retro の提案先」という役割を持つ（台帳に所在を書く）
- review-log の形式（source / severity / category / action）が計測と振り返りの共通契約になる
