# 0007: dev-team 自身の仕様も SSoT として持ち、日付付き設計書を畳む

- ステータス: accepted（2026-08-20）

## 背景
ADR 0005 は「アプリ仕様は SSoT の生きたドキュメント群で持ち、機能ごとの日付付き仕様書は積まない」と決めた。しかし dev-team 自身の仕様は `docs/specs/2026-08-15-dev-team-plugin-design.md` という日付付きの単発設計書に置かれており、自分で定めた原則に違反していた。

さらにこの設計書は「決定の経緯」（2章 検討したアプローチ・3章 決定事項16件）と「現在の仕様」（4章）と「進捗」（6章 移行手順・7章 着手順）を1ファイルに同居させていた。結果として次の実害が出た。

- データ置き場が設計書・ADR では `.claude/dev-team/`、実装では `.claude/dev-loop/` と食い違い、どちらが正か判断できない
- 4.5「dev-loop の新フロー」は未実装だが、実装済みの現行フローと同じ書式で書かれており、読み手が現状と将来を区別できない
- 決定16件は ADR 0001〜0006 と完全に重複し、二重管理になっていた

## 決定
- dev-team 自身の仕様も SSoT として `plugins/dev-team/docs/spec/` に持つ。領域ごとに1ファイル（`README.md` / `data-contracts.md` / `loop.md` / `intake.md` / `setup.md` / `retro.md`）
- 決定の経緯は ADR に一本化する。仕様書に決定理由を書かず、該当 ADR 番号を参照する
- 進捗（着手順・移行手順・未決事項）は仕様ではないので `docs/ROADMAP.md` に分ける
- **フレームワーク自身の仕様では、未実装のセクションも残す**。各セクション冒頭に `状態: 実装済み` / `状態: 未実装（ロードマップ <段階>）` を明記して区別する
- 旧設計書 `docs/specs/2026-08-15-dev-team-plugin-design.md` は SSoT へ取り込んだ後アーカイブする

## 検討した選択肢
- 設計書のまま維持する: ADR 0005 を自分で破っている状態が続き、原則の説得力が失われる。実際に SSoT 分裂の実害が出ていた
- 未実装セクションを仕様から消す（ADR 0005 に完全準拠）: プロダクトのアプリ仕様なら正しいが、フレームワークの仕様では設計意図が失われる。「なぜ draft PR にするのか」を消すと、実装時に再度同じ検討をやり直すことになる
- 仕様を ADR だけで表現する: ADR は決定の単位であって仕様の単位ではない。「現在どう動くか」を通して読めない

## 影響
- ADR 0005 の原則は維持しつつ、「未実装を書かない」の例外をフレームワーク自身の仕様に認める（プロダクトのアプリ仕様には従来どおり適用する）
- 仕様の変更時は `docs/spec/` を直し、決定を伴うなら ADR を追加する二段構えになる
- 状態表記（実装済み / 未実装）の更新漏れが新たな腐敗要因になりうるため、実装完了時に必ず更新する
