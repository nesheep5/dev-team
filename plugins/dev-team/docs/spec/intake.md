# spec-intake（要件 → 仕様・ADR・チケット）

人と壁打ちして要件を整理し、dev-loop が Issue 本文だけで実装できる状態まで具体化する。実装の詳細手順は [SKILL.md](../../skills/spec-intake/SKILL.md) にある。

## 成果物

状態: 一部実装（チケットのみ実装済み。仕様差分と ADR は未実装）

3種類を作る。

| 成果物 | 条件 | 状態 |
|---|---|---|
| チケット（Issue） | 常に | 実装済み |
| 仕様差分（SSoT の更新） | 仕様が変わるとき | 未実装（段階4） |
| ADR | 設計判断があったとき | 未実装（段階4） |

## 手順

状態: 一部実装（手順2・6・7 は未実装）

1. **要件ヒアリング**: 目的（なぜ必要か）を1〜3文で言語化して合意する
2. **仕様の現状確認**（未実装）: SSoT の関連セクションを読み、「今の仕様 / この要件が変える箇所」を提示する。コードにはあるが仕様に無い挙動が見つかれば、先に現状を仕様に書き起こしてから差分を議論する
3. **壁打ち**: プロダクトのドメインに関わる要件なら、該当するドメインスペシャリストのスキルがあれば読み込み、その観点から意見・懸念・代替案を出す。設計判断が分かれる点は選択肢と推奨を提示し、決定を ADR 候補としてメモする
4. **設計合意とチケット分割**: 1チケット = 1PR に収まる規模へ分割し、依存順を決める
5. **受け入れ条件の合意**: 検証可能な条件（入出力の具体例、通過すべきコマンド）をリストで提示する。「テスト・lint・build が全通過」は常に含める。`[ui]` / `[e2e]` マークを付ける（マークは未実装）
6. **成果物の PR**（未実装）: ブランチ `spec/<slug>` で仕様差分（アンカー付き）と ADR を出す。本文にチケット一覧を書く
7. **仕様 PR のマージ**（未実装）: 台帳の承認フローに従う（既定は会話合意による自動マージ。CI があれば緑を待つ）
8. **チケット作成**: 設計欄に仕様セクション参照と ADR 番号を書く。依存順に1件ずつ作成し、出力された Issue 番号を後続チケットの `depends: #N` に反映してから次を作る

「仕様マージ → チケット作成」の順にするのは、チケットが参照する仕様セクションが main に存在する状態を保つため。

## 対象プロジェクトの指定

状態: 実装済み

manager（[manager.md](manager.md)）が cwd 以外のリポジトリへ起票するとき（開発フロー・スキル・ルール・設定の改善を、`DEV_TEAM_FLOW_REPO` で指定したリポジトリへ迂回するとき。ADR 0013・0014）、対象は cwd ではなく `<path>` で渡される。手順は変えず、参照先だけ変える。cwd と対象が同じ通常の起票では、この節は使わない。

- SSoT・ADR・`package.json` 等の読み込みは `path` 起点の絶対パスで行う
- `gh` は常に `-R <owner/repo>` を付ける（`gh repo view --json nameWithOwner` を `path` で引く）
- ラベルの初回作成も `-R` 付きで行う

## ショートパス

状態: 実装済み

typo や明白なバグなど設計判断が不要な修正は、手順2〜3を省略し受け入れ条件だけ合意して起票する。仕様変更なし・ADR なし。

**仕様と実装のずれを直すバグでは仕様側が正**であり、仕様は触らない。

## 仕様の初期化

状態: 未実装（ロードマップ 段階4）

SSoT が無いプロダクトでは setup が `README.md` の雛形だけ作る。既存アプリの仕様書き起こしは spec-intake の初回に「領域分けの提案 → 領域ごとに現状をコードから書き起こす」チケット群として起票し、dev-loop が処理して人がレビューで正しさを確認する。日付付きの旧仕様書は SSoT に取り込んだ後アーカイブする。

## dev-loop からの差し戻し

状態: 未実装（ロードマップ 段階4）

設計判断不足で blocked になったチケットは、Issue コメントを入力に `/dev-team:spec-intake #N` で再度回す。決定を ADR と仕様に反映し、設計欄を更新して `status:ready` に戻す。

## 規約

状態: 実装済み

- Issue は dev-loop への唯一のインターフェース。本文に書かれていないことは実装されない前提で書く
- 詳細設計が別ドキュメントにあるときは本文へ転記せず、パスで参照する（二重管理の禁止）
- `depends: #N` は実装上の前提があるときだけ書く。着手順の希望だけでは書かない
