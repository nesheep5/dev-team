# dev-metrics / dev-retro（計測と振り返り）

状態: 未実装（ロードマップ 段階5）

## 設計の前提

フィードバックは**提案型**である（ADR 0004）。dev-loop は指摘と摩擦を記録するだけで、教訓ファイルへの自動追記はしない。誤った教訓が人の目に触れずに蓄積し、以後の実装を歪めるリスクを避けるため。

計測は **GitHub を正**とし、集計はスクリプトが行う。LLM に集計させない（数字がぶれるため）。

## dev-metrics

集計は `scripts/metrics.mjs`（Node、依存なし）が `gh` の出力から行い、スキルは結果を Markdown レポートに整える。

**指標**

- PR 数/日、マージ数/日
- ラリー回数（source 別）。1往復は PR 上の「レビュー（bot/人）→ 後続コミット」の組
- リードタイム（ready → merged、PR 作成 → 人の承認）
- blocked 率と理由の内訳
- 人の最終レビュー指摘件数

サブエージェントの往復は GitHub に痕跡が無いので events.jsonl / review-log から補完し、欠けていれば「不明」と表示する。**欠測を 0 と混同しない**ことが重要である。

起動は `/dev-team:dev-metrics [期間]`、`--out` で保存。dashboard は同じスクリプトを呼ぶ。

## dev-retro

入力は dev-metrics の結果・review-log・friction-log・blocked コメント・events.jsonl・各 SKILL.md・台帳。出力は3種類で、いずれも**提案止まり**。

### 出力1: プロダクトの開発ルールへの提案

繰り返し出た指摘（同 category が閾値以上、または `human:*`）を根拠付きでルール文案にし、台帳が指す開発ルール文書への PR を作る。決定を伴えば ADR 案も同じ PR に含める。

入力は **review-log**。プロダクトのコードに繰り返し現れる問題が対象。

### 出力2: プラグイン自身のスキル改修案

どの工程のどの手順がどういう失敗を生んでいるかを根拠付きで列挙する。人が承認したものは、フロー改善の起票先リポジトリ（`DEV_TEAM_FLOW_REPO`、ADR 0014）への PR にする。

入力は **friction-log**。review-log ではない。レビュアーが「プロダクトのバグ」を見つけたことは dev-team の指示の質を何も語らないため、両者を混ぜると信号が薄まる。

集計は `step` フィールドで行う。同じ `step` が複数チケットから報告されていれば、その節の記述に問題がある。報告は次の形にする。

```
step: review-arbitration（dev-loop）
  報告 3 件 / kind: ambiguous×2, human-intervened×1
  #42「裁定基準が受け入れ条件だけでは足りなかった」
  #47「レビュアー間で判断が割れ、独断で決めた」
  #51「人に聞いて初めて進めた」
  → 該当箇所: SKILL.md「レビュー反復」の裁定ルール
```

**根拠となる報告を必ず添える**。改修案だけを出すと、人が妥当性を判断できない。

### 出力3: 新スキルの提案

同型の blocked や手作業の繰り返しを指摘する。

## 起動と記録

`/dev-team:dev-retro [期間]` でオンデマンド実行する。毎ループ終了時のフル振り返りはコストが高く、報告が長くなって読まれなくなるため（ADR 0004）。

dev-loop の終了報告には**振り返り推奨シグナルだけ**を添える。

| シグナル | 既定閾値 |
|---|---|
| 同型 blocked | ≥ 2 |
| 人の指摘件数 | 前回より増 |
| ラリー平均 | > 2 |

閾値は台帳で変更可。

実行結果は `docs/retro/YYYY-MM-DD.md` に残し、人が採否を追記できるようにする（置き場所はドキュメント運用ルールで変更可）。

## friction-log をどう書かせるか

friction の記録は dev-loop の責務である（形式は [data-contracts.md](data-contracts.md)）。設計上の要点は3つ。

1. **詰まった瞬間に書く**。チケット完了時にまとめて振り返ると、記憶からの再構成になり「仕様がもう少し明確だとよい」のような一般論に流れる。欲しいのは具体的な躓きである
2. **`step` は安定 ID**。自由記述だと集計できない。SKILL.md の節に対応する ID を使う
3. **書かないことを責めない**。自己申告は必ず漏れる。漏れを前提に、blocked コメントと `human:*` の指摘で裏を取る
