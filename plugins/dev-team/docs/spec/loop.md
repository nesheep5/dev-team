# dev-loop（自律開発ループ）

`status:ready` のチケットを1件ずつ処理し、尽きたら結果を一括報告する。実装の詳細手順は [SKILL.md](../../skills/dev-loop/SKILL.md) にある。ここでは工程の構造と契約を定める。

## 状態遷移

状態: 一部実装（`awaiting-review` と自動ゲートは未実装。現行は「レビュー反復合格 → 即マージ」）

**目標フロー**（ADR 0002）

```
ready ─選択─▶ in-progress ─PR(draft)─▶ 自動ゲート ─合格─▶ awaiting-review ─Approve─▶ merged
                  │                       │ 3往復超 / 設計判断不足            │ Request changes
                  └───────────────────────┴─▶ blocked                        └─▶ 修正して再度 awaiting-review
```

**現行フロー**（実装済み）

```
ready ─選択─▶ in-progress ─PR─▶ レビュー反復(最大3) ─合格─▶ 即マージ ─▶ closed
                                      │ 3回超 / 解決不能
                                      └─▶ blocked
```

差分は「draft PR にするか」「人の Approve を待つか」「自動ゲートに CI と外部レビューを含むか」の3点である。

## 不変ルール

状態: 一部実装（`awaiting-review` と人の往復は段階 3b、台帳での変更は段階 2 で未実装。現行は「同時に 1 件」「レビュー反復は最大 3 回」）

- main へ直接コミットしない。変更は必ず PR 経由
- チケット PR のマージは squash に固定（1チケット = main 上の1コミット）。台帳で変更可（台帳は未実装）
- 同時に**実装中**のチケットは1件のみ（`awaiting-review` は複数可）
- 自動ゲートの往復は最大3回。人の往復は無制限（ADR 0002）
- 実装で解決できない問題（設計の矛盾・依存の不足・検証不能な受け入れ条件）は粘らず blocked にする
- 仕様に無い設計判断が必要になったら blocked にして spec-intake へ差し戻す。dev-loop は ADR を書かない（ADR 0005）

## 起動関門

状態: 実装済み（ADR 0009）

対話セッションでユーザーが dev-loop を名指しせずに依頼し、スキルが自動選択された場合は、`status:ready` の件数と先頭数件のタイトルを示して開始の許可を得る。許可が出るまで起動時チェック（副作用あり）に入らない。`/dev-team:dev-loop` の明示起動と、サブエージェント・Workflow・headless など回答者のいない実行では確認しない。

## 環境の回収

状態: 実装済み

ループはネットワーク切断・スリープ・セッション死で、後片付けを一切実行できない形で終わりうる。そのため**起動時と終了前に必ず回収を回す**。回収は記録ファイルではなくシステム状態から孤児を発見する方式にする（記録は再起動やプロセス入れ替わりで嘘になるため）。

対象は2つ。

| 対象 | 孤児の判定 | 順序 |
|---|---|---|
| 開発サーバー | `lsof` で LISTEN 中のプロセスの cwd が `.claude/worktrees/` 配下 | 先 |
| ワークツリー | `git worktree list` に無いディレクトリが `.claude/worktrees/` にある | 後 |

サーバーを先に止める。起動中のサーバーが `.next` を掴んでいるとワークツリー削除に失敗するため。

サーバーの停止は dev-loop に同梱した `scripts/stop-dev-server.sh` で行い、生の `kill` は使わない。スクリプトは `--root`（`<メインリポジトリ>/.claude/worktrees`）の外に cwd を持つプロセス、LISTEN していないグループ、シェルや claude 本体などの保護対象を含むグループを止めずに拒否する（ADR 0014）。拒否されたら別の手段で止めず、終了報告で人に依頼する。

ワークツリーの削除は「対応 Issue が closed」かつ「ビルド生成物以外のファイルが無い」の両方を満たすものだけに限る。片方でも怪しければ人に委ねる。ディスクを空けることより作業を失わないことが優先である。

## チケット選択

状態: 一部実装（`awaiting-review` の考慮は未実装）

1. `status:ready` の候補を取得する
2. `priority:high` を先に、同順位は Issue 番号の昇順
3. 補足の `depends: #N` を確認し、依存先が **closed でない**チケットはスキップする。`awaiting-review`（未マージ）もスキップ対象（ADR 0002 決定4。未マージブランチ上に積むリベース地獄を避ける）
4. 候補がゼロなら終了報告へ。ただし「ready はあるが全件が依存待ち」の場合は依存チェーンが詰まっている状態なので、ボトルネックの Issue 番号を明示する

## 実装

状態: 一部実装（開発ルール・仕様・ADR の事前読み込みは未実装）

ワークツリー `.claude/worktrees/ticket-<N>` で作業する。新規ワークツリーには依存物が無いため、まずパッケージマネージャで依存をインストールする。

着手前に読むもの（未実装）は、台帳が指す開発ルール・Issue が指す仕様セクション・関連 ADR。

TDD で実装し、コミットは1目的1コミット、メッセージは日本語。`[e2e]` 付きの受け入れ条件は Playwright テストをコード化して検証コマンドに含める（未実装）。

## 自動ゲート

状態: 未実装（ロードマップ 段階3b・3c）。現行は、ローカルでの検証コマンドと、手順 3〜5 のサブエージェントレビュー（spec-reviewer を除く）・裁定・review-log への記録のみ。CI と外部レビュアーは待たない

最大3往復。

1. **CI 待ち**（`gh pr checks --watch`）。失敗は `source:ci` の指摘として扱う
2. **外部レビュアー待ち**。台帳に外部 AI レビュアーと待機時間があれば PR コメント/レビューの到着を待つ。無ければスキップ（ADR 0003）
3. **サブエージェントレビュー**（並列）: pr-review-toolkit の code-reviewer / pr-test-analyzer / silent-failure-hunter + プラグインの spec-reviewer。pr-review-toolkit が無い環境では汎用エージェントで代替（ADR 0003）
4. **指摘の統合・裁定**: 同一箇所の重複は1件。バグ・データ破壊・セキュリティ・仕様不一致は常に高重要度。設計趣味・スタイル・スコープ外の改善提案は受け入れ条件で裁定する。全件を review-log に記録し、高重要度を修正して 1 に戻る
5. **合格基準**: 高重要度ゼロかつ CI 緑

修正が新たな高重要度指摘を生む往復が続く場合は設計側の問題である可能性が高い。3回の上限を待たずに blocked にしてよい。

## UI 動作確認

状態: 未実装（ロードマップ 段階3c）

自動ゲート合格後、ui-verifier がワークツリーで dev サーバーを動的ポートで起動し、`[ui]` 付き受け入れ条件を Playwright MCP で操作確認する。結果とスクリーンショットを PR コメントに投稿する。不合格なら修正して自動ゲートを再実行（往復回数に数える）。`[ui]` が無ければスキップ（ADR 0003）。

## 人へ引き渡し

状態: 未実装（ロードマップ 段階3b）

`gh pr ready` → レビュアー指定（台帳の既定レビュアー、無ければリポジトリオーナー）→ `status:awaiting-review` → 次のチケット選択へ。承認を待って居座らない。

## 回収フェーズ

状態: 未実装（ロードマップ 段階3b）

起動時と終了前に `status:awaiting-review` の PR を PR 番号順に見る。

- **最新コミットに対して Approved かつ CI 緑** → main 取り込み → 検証 → squash マージ → 後片付け（サーバー停止・worktree 削除・Issue close・ラベル外し）
- **main 取り込みでコンフリクト** → blocked コメントを残し人に委ねる
- **Request changes / 新しい人のコメント** → 指摘を review-log に `human:<login>` として記録 → 修正 → push → 再レビュー依頼
- **コードで解決できない指摘** → スレッドで返信し awaiting-review のまま残す

「最新コミットに対する Approve」を条件にするのは、stale approval の扱いがブランチ保護の設定次第で変わるため。

## blocked 処理

状態: 実装済み

1. ラベルを `status:blocked` に付け替える
2. 何を試し何が解決できないかを Issue にコメントする
3. PR とブランチは open のまま残し、ワークツリーも残す。ただし**開発サーバーは停止する**（再開が数日後になることもあり、その間動かし続ける理由がない）

## 終了報告

状態: 一部実装（人のレビュー待ちと振り返りシグナルは未実装）

回収フェーズと環境の掃除を回してから、1つの報告にまとめる。

- マージ済み: Issue 番号・タイトル・PR 番号
- blocked: 今回分だけでなく**現在 blocked 状態の全チケット**。依存チェーンのボトルネックは明示する
- スキップ（依存待ち）: Issue 番号・待っている依存先
- 人のレビュー待ち（未実装）: `awaiting-review` の一覧。次回起動時に回収する旨
- 開発サーバー: 停止したポート。前回の中断から回収した孤児があれば件数とポートを明示する
- ワークツリー: 削除した孤児の件数。保留したものはパスと理由
- 振り返り推奨シグナル（未実装）: 同型 blocked ≥ 2、人の指摘件数が前回より増、ラリー平均 > 2。閾値は台帳で変更可
- 人への依頼: 動作確認ポイント、blocked の判断依頼。サーバーは停止済みなので再開コマンドを添える

## manager への報告

状態: 実装済み

manager（[manager.md](manager.md)）から「終了報告はこの送信元へ返信」というセッション間メッセージを受けていれば、終了報告を SendMessage でその `from` へ送る。受けていなければ従来どおり画面に出すだけ。報告の内容は「終了報告」節と同じ。

blocked 処理は変えない。人の判断が要る事項は Issue コメントに残り、manager が巡回で拾う。

## イベント書き出し

状態: 実装済み

処理の節目で `events.jsonl` に追記する（形式は [data-contracts.md](data-contracts.md)）。

| タイミング | イベント |
|---|---|
| ループ開始 | `event:"loop"`, `detail:{"action":"start"}` |
| チケット選択 | `stage:"selected"` |
| 実装開始 | `stage:"implementing"` |
| 検証コマンド実行 | `stage:"verifying"` |
| PR 作成 | `stage:"pr-created"`, `detail:{"pr":<番号>}` |
| レビュー反復の各回開始 | `stage:"review"`, `detail:{"iteration":<n>,"reviewers":[...]}` |
| レビュー指摘の修正開始 | `stage:"fixing"` |
| マージ処理開始 / 完了 | `stage:"merging"` / `stage:"merged"` |
| blocked 処理 | `stage:"blocked"`, `detail:{"reason":"<要約>"}` |
| 依存待ちスキップ | `stage:"skipped"`, `detail:{"reason":"依存 #N 待ち"}` |
| 特記事項 | `event:"log"`, `detail:{"text":"<内容>"}` |
| ループ終了 | `event:"loop"`, `detail:{"action":"end"}` |

段階3b で `awaiting-review` / `approved` / `ui-verifying` を追加する。
