# spec-intake — 要件を開発チケットにする

dev-loop が Issue 本文だけで実装できる状態まで要件を具体化し、`status:ready` の Issue として登録する。

## 手順

1. **要件ヒアリング**: 持ち込まれた要件を聞き、目的（なぜ必要か）を1〜3文で言語化して合意する
2. **壁打ち**: 要件がプロジェクトのドメイン（業務知識・ユーザーのワークフロー）に関わる場合、該当するドメインスペシャリストのスキルが利用可能なら読み込み、その観点から意見・懸念・代替案を提示する。該当スキルが無ければこのステップをスキップする
3. **設計合意**: 実装方針を提示し、承認を得る。1チケット = PR 1本に収まらない規模なら複数チケットに分割し、依存順を決める
4. **受け入れ条件の合意**: 検証可能な条件（入出力の具体例、通過すべきコマンド）をリストで提示し、合意する。「プロジェクトのテスト・lint・build が全通過」は常に含める（コマンドは package.json の scripts・Makefile 等から特定する）
5. **Issue 作成**: 下のフォーマットで作成し、`status:ready` を付与する。緊急なら `--label "priority:high"` を追加する（`--label` は複数指定できる）。複数チケットに分割した場合は**依存順に1件ずつ作成**し、出力された Issue 番号を後続チケットの「補足」の `depends: #N` に反映してから次を作成する。本文ファイルはリポジトリ外に作成し、チケットごとに別名にする（例: スクラッチパッド配下の `ticket-<連番>.md`）。作成後に削除する

```bash
# --label "priority:high" は緊急時のみ付ける
gh issue create --title "<変更内容の要約>" --label "status:ready" --label "priority:high" --body-file <本文ファイル>
rm <本文ファイル>
```

ラベル（`status:ready` / `status:in-progress` / `status:blocked` / `priority:high`）がリポジトリに未作成なら、初回に `gh label create` で作成する。

## 対象プロジェクトの指定

manager（`/dev-team:manager`）が cwd 以外のリポジトリへ起票するとき（開発フロー・スキル・ルール・設定の改善を、環境変数 `DEV_TEAM_FLOW_REPO` で指定したリポジトリへ迂回するとき）は、対象のリポジトリパス `<path>` が渡される。手順は変えず、参照先だけ次のように変える。

- SSoT・ADR・`package.json`・Makefile・コードの読み込みは `<path>` 起点の絶対パスで行う（検証コマンドの特定は `<path>/package.json` の scripts 等から）
- `gh` は常に `-R <owner/repo>` を付ける。`owner/repo` は `cd <path> && gh repo view --json nameWithOwner -q .nameWithOwner` で引く
- ラベルの初回作成も `gh label create -R <owner/repo> ...` で行う
- Issue 本文ファイルはスクラッチパッド配下に作る（cwd のリポジトリに残さない）

```bash
gh issue create -R <owner/repo> --title "<変更内容の要約>" --label "status:ready" --body-file <本文ファイル>
```

cwd と対象が同じ通常起動では、この節は無視してよい。

## ショートパス

typo や明白なバグなど設計判断が不要な修正は、手順2〜3を省略し、受け入れ条件だけ合意して Issue 化する。

## Issue フォーマット

「目的 / 設計 / 受け入れ条件 / 補足」の4セクション構成で書く。プロジェクトに開発チケット用の Issue テンプレート（`.github/ISSUE_TEMPLATE/`）があればそちらの構成に従う。

- **目的**: なぜ必要か（1〜3文）
- **設計**: 実装方針。参照すべきドキュメントやコードのパス
- **受け入れ条件**: 検証可能な条件のチェックリスト
- **補足**: 依存関係（`depends: #N`）・経緯・スコープ外事項

## 規約

- Issue は dev-loop への唯一のインターフェース。本文に書かれていないことは実装されない前提で書く
- 詳細設計が別ドキュメントにあるときは本文へ転記せず、パスで参照する（二重管理の禁止）
- 依存関係は「補足」に `depends: #N` と書く。dev-loop は依存先が closed でない間このチケットをスキップする
- `depends: #N` は**実装上の前提**があるときだけ書く（先行チケットの型・関数を使う等）。単に着手順の希望があるだけなら書かない。依存を直列に連ねると、1件が blocked になった時点で後続すべてが着手不能になる
